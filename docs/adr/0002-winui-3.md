# ADR 0002: WinUI 3 on Visual Studio 2026 with a Hybrid Build

- **Status:** Accepted
- **Date:** 2026-10-04 (recorded and source-checked 2026-10-08)
- **Decider:** the operator, as recorded in D00 T02
- **Supersedes:** the compiler baseline, UI framework, app build, and single-file distribution assumptions in [ADR 0001](0001-tech-stack.md)

## Context

The operator requested "VS C++ (2026 - latest) with WinGUI 3 (latest)" on 2026-10-04. The plan interprets "WinGUI 3" as WinUI 3 and records the operator's choices of a hybrid build and unpackaged, self-contained distribution. This decision changes the app technology while retaining the tested core and storage boundaries. The implementation is sequenced in [D00 T02](../../todo/00-workspace/TODO-02-winui-stack.md); accepting this ADR does not claim that the replacement shell already exists.

## Decision

Use C++20 with Visual Studio 2026 and the v145 toolset. Build the app with WinUI 3 through C++/WinRT and pin `Microsoft.WindowsAppSDK` to stable version 2.5.1. Microsoft still identifies 2.5.1 as its latest stable release on the source-check date; experimental releases are excluded. Section 2 pins the exact C++/WinRT and NuGet tool versions with their provenance.

Keep CMake presets and Ninja for `spellbook_core`, `spellbook_storage`, and their tests. Build the app as `src/app/Spellbook.vcxproj` in the root `Spellbook.slnx`, using MSBuild and the libraries produced by CMake. The repository runners will sequence both systems and keep configuration, architecture, warnings, dependencies, and CRT choices consistent. The replacement app's XAML and generated C++/WinRT sources are built by MSBuild; CMake will no longer compile the app target.

Ship an unpackaged, self-contained application folder, with `WindowsPackageType=None`, `AppxPackage=false`, and `WindowsAppSDKSelfContained=true`. The portable ZIP contains that folder, and Inno Setup 7 installs the same payload. The Windows App SDK runtime travels with the application; deployment must preserve all required runtime files, generated resources, and the executable together. The existing three installer modes from ADR 0003 remain: current user, all users, and portable.

Keep the existing product identity, SQLite schema and transactional migration contract, logging behavior, `--data-dir`, and smoke-mode contract. Core remains independent of Windows and UI headers; storage remains independent of the app. WinUI handles presentation, with Win32 interoperability at the native boundary when needed. No product feature or database change is authorized by this ADR alone.

## Alternatives considered

| Alternative | Operator's selected direction and consequence |
| --- | --- |
| Move all targets to MSBuild | Keep the hybrid build, retaining the library presets, tests, and compilation databases while accepting a second build system for the app. |
| Ship an MSIX package | Use unpackaged distribution, retaining the portable folder and classic Inno Setup installer. Package identity and Store-specific packaging remain separate planned work. |
| Use framework-dependent deployment with a runtime installer | Bundle the Windows App SDK runtime with the app, accepting a larger payload and responsibility for shipping runtime updates. |
| Keep the Win32-only shell | Replace it with the requested WinUI 3 surface; preserve its startup and data behavior through section 3's parity checks. |

## Section 3 implementation decisions

### CRT compatibility

Retain `x64-windows-static` and the static CRT consistently across app, core, and storage: `/MT` in Release and `/MTd` in Debug. Both hybrid builds link successfully with Windows App SDK 2.5.1 and C++/WinRT 3.0.260818.1. The Debug shell passes first-frame smoke, schema-1 readback, restart, space-containing paths, and noninteractive failure probes. Build and probe receipts are under `build/winui-evidence/`; clean-machine deployment remains a required checkpoint before the section is stamped.

If the WinUI app cannot link or start with the static CRT, switch every target to the dynamic CRT and use `x64-windows-static-md` for vcpkg. Ship the redistributable VC++ runtime app-local in the release folder. Cost: changing the triplet rebuilds the vcpkg binary cache and every target, and requires all gates and deployment checks to run again. Mixing CRT choices between the app and linked libraries is not the fallback.

### Static analysis of the app

Retain clang-tidy for core, storage, and tests, and use MSVC Code Analysis for the app project. The pinned clang-tidy 22.1.8 parsed `App.xaml.cpp` with the actual generated headers and MSBuild include/define settings, but reported three diagnostics inside generated `winrt/base.h`: a nullable COM dispatch and two partially initialized string-reference reports. Its generated-header boundary is not a usable clean app gate without additional adapter/suppression work. This is a tooling limitation, not a claim that Clang cannot parse WinUI. The full trial is in `build/winui-evidence/app-clang-tidy.log` with its exit receipt.

MSVC analysis passes the app project with `/analyze`, `/W4 /WX`, and `/analyze:external-` for vendor headers. The initial vendor fmt diagnostic and successful external-header configuration are retained in `build/winui-evidence/msvc-analysis-first.log` and `build/app-analysis-debug.log`. The hybrid lint runner and CI enforce this path now; no owned app warning is disabled. Library lint checks native exit codes and ignores only unsupported MSVC command-line switches in Clang's parser.

The app uses native C++ `PackageReference` with `EnableNativePackageReferenceSupport=true`, so setup now requires VS 2026 18.7 or newer. CMake generates the package-version imports directly from `toolchain.json`, then MSBuild restores them. This preserves one version source while using the native project model in Microsoft's current self-contained sample.

## Consequences and rollout

- Distribution becomes a folder rather than one executable. Packaging, installation, updates, and portability checks must preserve the complete payload.
- Two build systems need explicit orchestration; no runner may silently skip the MSBuild app after the migration.
- Section 2 changes toolchain discovery and pins; section 3 replaces the shell and resolves the open questions; section 4 updates runners, CI, and packaging; sections 5 and 6 update UI guidance and open feature contracts.
- Section 3 replaces the CMake-built Win32 bootstrap with the hybrid WinUI shell. Later runner and documentation sections retain their remaining contracts; passing library tests alone never prove the shell or its deployment.
- The Windows 10 1809+ and Windows 11 support requirement remains subject to the planned deployment and visual checks. No clean-machine WinUI result is claimed here.
